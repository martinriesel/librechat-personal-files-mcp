# DECISIONS.md — technical decisions beyond the original briefing

This file records every decision made during implementation that goes beyond the
original project briefing, so future maintainers understand *why* things are the
way they are.

---

## D001 — Build backend and packaging
**Decision:** Use `hatchling` as build backend with a single `pyproject.toml` (PEP 621).
**Reason:** Modern standard Python 3.12 stack; avoids legacy `setup.py`/`setup.cfg`; supports `src/` layout.

## D002 — MIME type detection
**Decision:** Use `python-magic` (libmagic) in `storage.stat()` and the public endpoint, with a `mimetypes` fallback when libmagic is unavailable.
**Reason:** More accurate than stdlib `mimetypes`; the fallback keeps it working on slim images.

## D003 — Tool return type contract
**Decision:** Every MCP tool returns structured text (`str`), never a raw exception. Errors follow `ERROR: <code> — <reason>`; success returns readable JSON.
**Reason:** Maximizes usefulness for the LLM and makes failures actionable.

## D004 — UUID v4 as `file_id` in rag_api
**Decision:** `file_id` sent to `POST /embed` is a `uuid.uuid4()` generated by the MCP and persisted in the docindex (`rag_file_id`). Never exposed to the LLM.
**Reason:** Avoids collisions/cross-user leakage and allows canonical `DELETE`.

## D005 — `/healthz` reports degraded mode
**Decision:** `GET /healthz` returns `{status, rag, storage, jwt_configured, version}`. Always HTTP 200; status is reflected in the body.
**Reason:** Keeps compatibility with simple probes while reporting degradation when `JWT_SECRET` is missing/weak.

## D006 — Tests run without network
**Decision:** Tests use `pytest` + `httpx` TestClient + `respx` mocks only. No real network calls.
**Reason:** Keeps CI green without rag_api/containers.

## D007 — Phase order
**Decision:** Implement phases A→B→C→F (packaging) before D/E, which depend on the operator restarting the stack.
**Reason:** Everything runnable locally is finished and tested first; D/E are instructions delivered to the operator.

## D008 — Stateless HTTP MCP + lifespan forwarding
**Decision:** Use `FastMCP.http_app(path="/mcp", stateless_http=True)` mounted at `/` on FastAPI, forwarding the MCP sub-app lifespan via `async with mcp_app.lifespan(app)`.
**Reason:** FastMCP 3.x requires the `StreamableHTTPSessionManager` to be initialized through the lifespan; without it, tool calls fail with "Task group is not initialized".

## D009 — AppContext and user_id access in tools
**Decision:** `AppContext` is attached to the `FastMCP` instance (`_app_context`); tools read it via `ctx.fastmcp._app_context`. The `user_id` is extracted and validated from `ctx.request_context.request.headers.get("X-User-Id")`.
**Reason:** In stateless HTTP mode the FastMCP `Context` does not expose `request` directly, but `request_context.request` is the original Starlette request (with headers). The parent middleware validates the header; reading headers directly keeps fail-closed consistent.

## D010 — `storage.resolve()` rejects `..` in any segment
**Decision:** `resolve()` rejects any occurrence of `..` as a path segment (including `a/../b`).
**Reason:** The briefing requires rejecting `..` in any segment.

## D011 — Umask applied as `0o666 & ~umask`
**Decision:** Written files get `os.chmod(path, 0o666 & ~umask)` (default `0o664` with umask 002); directories use `0o777 & ~umask`.
**Reason:** `Path.write_bytes()` creates files with process umask; applying `chmod` post-write with base 0o666 guarantees group-writable (0o664) per `UMASK=002`.

## D012 — Pattern filter applies to files only during recursive listing
**Decision:** In `storage.list(recursive=True, pattern=...)`, `fnmatch` is applied only to files; directories are always traversed.
**Reason:** Otherwise a directory named e.g. `docs` would be filtered by `*.md` and its nested matches (`docs/b.md`) would never be visited.

## D013 — Canary phrase extraction
**Decision:** `rag_client._canary_phrase()` skips empty lines and headings (`# `), strips control chars, and returns the first 80 chars of the first meaningful non-heading line. If no phrase can be extracted, it trusts the embed response.
**Reason:** Deterministic post-index verification (upstream issue #305).

## D014 — Public endpoint bypasses IdentityMiddleware
**Decision:** `IdentityMiddleware` bypasses `/healthz` and `/files*`. `/files/{token}` validates the token against the registry.
**Reason:** Public links must be reachable without the agent's `X-User-Id`; the opaque token is the credential.

## D015 — MCP served at `/mcp` without trailing-slash redirect
**Decision:** Mount the MCP sub-app at root `app.mount("/", mcp_app)` with `http_app(path="/mcp")`, registering `/healthz` and `/files/{token}` before the mount. Add an explicit 405 handler for non-GET/HEAD on `/files`.
**Reason:** `app.mount("/mcp", ...)` with `path="/"` made Starlette emit a 307 from `/mcp` to `/mcp/`, which the LibreChat streamable-http client (pointing at `/mcp`) may not follow reliably.

## D016 — Storage directories created in the Docker image
**Decision:** Create `/data/private`, `/data/share`, `/data/private/_system` in the image with `chown 2000:2500` before `USER mcp`.
**Reason:** The container runs as non-root (UID 2000); without pre-created directories startup fails with `PermissionError: /data` when the host bind is not mounted yet.

## D017 — Non-editable install in the Docker builder
**Decision:** In the builder stage use `pip install ".[dev]"` (non-editable) instead of `pip install -e`.
**Reason:** Editable installs generate a `.pth` pointing to `/build/src`, which does not exist in the runtime stage (which only copies `/opt/venv`), causing `ModuleNotFoundError`. A regular install places the package in `site-packages`.

## D018 — Nginx: proxy `/files/`, legacy `/share/`, internal `/_protected/`
**Decision:** Replace the legacy `location /files/` (which served static files from `/data/share`) with `proxy_pass` to the MCP; keep legacy files under `location /share/`; add `location /_protected/` (`internal` + `alias /data/private/`) for X-Accel-Redirect; add `limit_req_zone`/`limit_req`; make `/data/private` world-executable (`chmod 2771`).
**Reason:** Nginx worker (alpine) runs as UID 101, outside group `lcfiles` (2500); `chmod 2770` blocked directory traversal, causing `Permission denied` on file serve. `o+x` allows traversal without listing.

## D019 — Public link Content-Type from the registry
**Decision:** `publishing._serve` sends `Content-Type` = `record.mime_type` on the X-Accel-Redirect response.
**Reason:** Without it Nginx used the default `application/octet-stream`; the correct MIME type is already persisted at `create_link`.

## D020 — rag_client adapted to the real rag_api
**Decision:** Rewrite the client to match the actual `rag_api` (dev/latest), which differs from the original briefing:
  - `/embed`: **multipart/form-data** (`file_id`, binary `file`, optional `entity_id`), not JSON.
  - `/query`: requires `file_id` (single-file search), owner-scoped via metadata `user_id`.
  - `/query_multiple`: searches several `file_ids`; **no** owner check — caller passes only the user's own file_ids.
  - `DELETE /documents`: body is a **list** of ids.
  - Response shape: `[[{page_content, metadata:{file_id,user_id}}, distance], ...]`.
**Tool impact:** `search_knowledge` uses `/query_multiple` with the user's docindex file_ids; `index_document` sends multipart + canary via `/query`; `remove_from_knowledge` sends a list. Ownership is preserved via JWT `id`/`sub` = userId.

## D021 — One HTTP client per RAG operation (event loop)
**Decision:** `tools._run_rag` runs each RAG operation in a single `asyncio.run` with one `RagClient` created and closed in the same loop.
**Reason:** `httpx.AsyncClient` is bound to the event loop it was created in; reusing it across multiple `asyncio.run()` calls raised `RuntimeError: Event loop is closed`.

## D022 — Canary: strip markdown before matching
**Decision:** `rag_client._clean_for_canary` applies `_strip_markdown` (removes `**bold**`, `*italic*`, backticks, headings, links) to the canary phrase.
**Reason:** The rag_api loader normalizes text (e.g. strips `**` and merges lines). Matching the raw phrase (with `**`) against the stripped chunk failed, causing a false `indexing_failed` and chunk deletion. Stripping markdown aligns the phrase with the loader output.

## D023 — Canary: also strip blockquote/list markers and skip horizontal rules
**Decision:** Extend `_strip_markdown` to also remove `>` blockquote markers, `-`/`*`/`+` list bullets, and `1.` ordered-list markers; `_clean_for_canary` skips horizontal rules (`---`, `***`, `___`).
**Reason:** Same class of failure as D022, but for documents starting with a blockquote or list. The rag_api loader strips `>`/bullets, but the canary kept them, so the substring match failed (e.g. `> MCP server ...` vs `MCP server ...`), causing a false `rag_canary_failed` and chunk deletion.

## D024 — Direct file delivery via Starlette FileResponse without Nginx
**Decision:** `publishing._serve` delivers files directly using `FileResponse` with `path=abs_path`, `content_disposition_type="attachment"`, `headers={"X-Content-Type-Options": "nosniff", "Cache-Control": "private, no-store"}`, and `method=request.method`. Eliminate the `X-Accel-Redirect` header and the dependency on Nginx's `/_protected/` alias.
**Reason:** On Dokploy and modern proxy setups using Traefik, `X-Accel-Redirect` is not handled, causing empty 200 responses. `FileResponse` streams files in chunks via ASGI without buffering entire payloads in memory, supports HTTP Range requests (206 Partial Content) natively, and allows direct deployment behind Traefik or any standard reverse proxy.

## D025 — Project context discovery and request-scoped diagnostics (Fase 3)
**Decision:** Implement `get_project_context` tool and request-scoped context tracking using `ContextVar[RequestContextData]`. Resolve project association via read-only MongoDB queries against `conversations` and `chatprojects` with strict user isolation (`{"user": user_id}`). On Turn 1 (new conversation race condition), apply up to 2 micro-retries (250ms backoff) before returning `conversation_unavailable` with `retry_recommended: true`, avoiding false `no_project` classification. Implement single-line JSON structured diagnostics enabled via `PERSONAL_FILES_CONTEXT_DIAGNOSTICS=true` with strict key sanitization.
**Reason:** LibreChat only provides `conversationId` via request headers (`{{LIBRECHAT_BODY_CONVERSATIONID}}`) and does not supply `chatProjectId` directly. Direct read-only resolution guarantees verified project association without trusting user/LLM input, while micro-retry resolves timing differences between tool execution and MongoDB conversation insertion.

## D026 — Project memory catalog schema v3 (Fase 4)
**Decision:** Upgrade `memory-index.json` schema to version 3 (`INDEX_VERSION = 3`). Add optional fields `project_id: str | None = None`, `project_name: str | None = None`, and `conversation_id: str | None = None` to `DocumentEntry`. Maintain 100% backward compatibility when loading v2 catalogs (defaulting missing fields to `None`) and upgrade automatically upon write. Update `save_documentation` and `update_documentation` to accept project parameters or auto-populate from active request context. Expose `list_documentation` MCP tool. Synchronize `docindex` on file renames (`move_file`) and deletions (`delete_file`). Include project document summaries and `summary_file` in `get_project_context()`.
**Reason:** Allows persistent memory across multiple conversations within a LibreChat project without requiring the agent to maintain duplicate catalogs or rely on folder naming conventions.

## D027 — Project-scoped RAG isolation and auto-scoping (Fase 5)
**Decision:** Add `project_id: str | None = None` and `scope: str = "auto"` to `search_knowledge`. In project conversations (`scope="project"` or `scope="auto"` with active project), restrict candidate `file_ids` sent to `client.query_multiple` strictly to documents where `entry.project_id == active_project_id`. If the active project has no indexed documents, return immediately with `count: 0` and an informative note without dispatching queries to `rag_api`. Support explicit personal (`scope="personal"`) and global (`scope="all"`) searches.
**Reason:** Guarantees strict multi-project isolation for semantic search. A conversation in Project A will never receive chunk matches or metadata from Project B or unrelated personal documents, avoiding context poisoning while eliminating wasted RAG API calls.

## D028 — Multi-scope catalog with physical separation
**Decision:** Maintain physically separate `memory-index.json` files: `docs/memory-index.json` for the general scope and `projects/<project_id>/memory-index.json` per project. Helper functions `get_project_catalog()`, `get_general_catalog()`, `get_catalog_for_path()`, `get_all_catalogs()`, `find_document_across_catalogs()`, and `list_all_documents()` abstract multi-catalog operations. The legacy root `memory-index.json` (if any) is preserved and readable but not the primary catalog.
**Reason:** Physical separation ensures that cross-process file locks on catalogs cannot block unrelated projects, simplifies backup/restore per project, and aligns catalog location with file location (`projects/<id>/` files indexed in `projects/<id>/memory-index.json`).

## D029 — Fail-closed routing for `save_documentation`
**Decision:** When the project resolver returns an error status (`conversation_unavailable`, `resolver_unavailable`, `project_unavailable`, `context_invalid`), `save_documentation` returns `ERROR: project_resolution_failed — <reason>` instead of silently falling back to the `docs/` directory. The fail-closed check is enforced in both `app.py` (MCP layer, which owns the resolver) and `tools.py` (via `resolver_status` parameter, defense-in-depth).
**Reason:** Silent fallback would scatter project documents into the general catalog with no trace, making later reconciliation nearly impossible. Explicit failure lets the LLM retry or ask the user for explicit routing.

## D030 — Catalog protection against LLM-initiated writes
**Decision:** `_is_protected_catalog_path()` rejects any path ending in `memory-index.json` or matching `*.lock`. All generic file tools (`write_file`, `update_file`, `delete_file`, `move_file`, `edit_file`, `write_binary_file`) call this guard before proceeding.
**Reason:** The user specified that the LLM must never write `memory-index.json` directly. All catalog mutations flow through dedicated tools (`save_documentation`, `register_documentation`, `transfer_documentation`, `reconcile_documentation`).

## D031 — Stable `doc_id` per document
**Decision:** Every `DocumentEntry` receives a persistent `doc_id` formatted as `doc_<uuid_hex12>`. The ID is generated once at creation and preserved through content updates, transfers, and re-indexing. Lookup functions (`DocIndex.get()`, `find_document_across_catalogs()`) accept `doc_id`, relative path, or basename.
**Reason:** Filenames can change (transfer, rename); a stable ID lets tools and external references survive path changes. The 12-hex-char suffix keeps IDs short enough for LLM tool calls.

## D032 — `transfer_documentation` with collision detection and link preservation
**Decision:** `transfer_documentation` moves the physical file, removes the entry from the source catalog, inserts it into the destination catalog (preserving `doc_id`, metadata, and RAG fields), detects target-path collisions, updates `LinkRegistry.update_path()` for public links, and supports `dry_run=true` for preview without side effects.
**Reason:** Transfer across scopes is a multi-step operation (file move, two catalog updates, optional link update). Collision detection prevents silent overwrites; dry-run lets the LLM show the user what will happen before committing.

## D033 — `index_batch` with factory closures
**Decision:** `index_batch` iterates candidate documents and dispatches them through the existing RAG pipeline. Inner `async def flow` and `async def cleanup` are created via factory functions (`make_flow`, `make_cleanup`) to bind loop variables, avoiding ruff B023 (function defined in loop uses mutable variable).
**Reason:** Batch indexing is the user's requirement for efficiency. The factory pattern satisfies both Python scoping semantics and ruff's lint rule without suppressing the warning.

## D034 — `list_projects` combines MongoDB and disk state
**Decision:** `list_projects` queries `chatprojects` from MongoDB (filtered by `{"user": user_id}`) and also scans `projects/` on disk. Projects found on disk but not in MongoDB are reported with `source: "disk_only"`. Each project entry includes `doc_count` and `indexed_count` from its catalog.
**Reason:** A project may exist in MongoDB but have no local documents (yet), or local documents may exist for a project ID that the user no longer owns in LibreChat. Combining both sources gives the LLM a complete picture for reconciliation decisions.

## D035 — Async tools never call `asyncio.run`
**Decision:** RAG calls from async MCP tools (`search_knowledge`) use `await _arun_rag(...)`, which creates and closes a `RagClient` in the server's event loop. Sync tools keep `_run_rag(...)`, which is safe because FastMCP runs sync tools in a worker thread without a running loop; `_run_rag` raises an explicit error if called from a running loop. Async tools are tested through the real HTTP → FastMCP transport, not only by calling `tools.*` directly. `nest_asyncio` is not used.
**Reason:** 1.4.0-test failed in production with `asyncio.run() cannot be called from a running event loop`; unit tests called the function outside any loop and missed it.

## D036 — `search_knowledge(scope="auto")` is fail-closed
**Decision:** `auto` resolves to `project` when the conversation has a project, and to `all` only when the resolver returns `no_project`. Every other resolver status returns `ERROR: project_resolution_failed` with `resolver_status` and `retry_recommended`, and `rag_api` is not queried. Explicit scopes (`all`, `personal`, `project` + `project_id`) do not consult the resolver.
**Reason:** Same rule as D029 for saving: a resolver failure is not proof of "no project", and must not silently widen a project-scoped search to every document.

## D037 — One project-membership rule for all tools
**Decision:** `docindex.effective_project_id(entry, catalog)` = `entry.project_id` if set, otherwise the `<id>` of a `projects/<id>/` catalog, otherwise none. `list_documents_with_catalog()` applies it across the project, `docs/` and legacy root catalogs, and is used by `list_projects`, `get_project_context`, `list_documentation`, `search_knowledge` and `index_batch`. Results expose the source `catalog` (`project`/`general`/`legacy`). Nothing is migrated.
**Reason:** `list_projects` counted only the project catalog while `get_project_context` also counted the legacy root catalog, so the same project showed 5 and 6 documents; documents in `docs/` linked by metadata were invisible to project search.
